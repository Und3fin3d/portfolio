A 5×5 chess engine, and porting it to JS

My second-year AI coursework was to write an agent for Chess Fragments, which is a 5×5 variant. Five files of board, five pieces a side, and the piece in the corner is the Right, which moves as a rook and a knight put together. Pawns keep their double push, en passant and promotion. The agents were graded by playing each other, so it was never really an exercise in getting the rules right, it was an exercise in searching deeper than whoever you were playing in the same amount of time.

It is the engine you can play on the front page, ported over to JavaScript. That port is the second half of this post and it went a lot less smoothly than the first.

Bitboards

With twenty-five squares a position fits into 25 bits, so every piece type for each colour is one integer and most of the questions you end up asking constantly turn into single instructions. Which squares do I occupy is an OR across my boards, whether a square is empty is one AND, and where a knight can go is a table lookup masked against my own pieces.

Sliding pieces are the harder case because a rook's moves depend on whatever is in the way. The usual answer is magic bitboards, where for each square you mask the occupancy down to only the squares that could block a ray, multiply that by a constant chosen so the scattered bits collapse into a dense index, shift it down, and use the result to look up the attack set in a table you built in advance. That is one multiply, one shift and one lookup, and the blockers are dealt with.

The constants themselves are not derived from anything. You find them by trying random numbers until one of them happens to produce no harmful collisions, check it exhaustively against every occupancy that square can see, and then paste it into the source.

Search

The search is negamax with alpha-beta under iterative deepening, so it searches to depth one, then depth two, then three, and carries on until the clock runs out, and then plays the best move from whichever depth finished last.

Searching shallow first sounds like it wastes time and it does the opposite. Alpha-beta only prunes properly when good moves get tried early on, and the previous iteration tells you which move looked best, so each pass makes the next one cheaper by more than the pass itself cost.

Time gets budgeted per move out of the clock that is left and roughly how many moves are still to play, with a bit held in reserve so it never flags.

Search enhancements

All of the above is textbook, and the depth really comes from the pruning that gets stacked on top of it.

Null-move pruning. You let the opponent move twice, and if their position is still bad after that then yours was good enough that the real move is going to beat the window anyway, so the whole subtree can be skipped.

Late move reductions. After the first few moves at a node the remaining ones are unlikely to be best, given the ordering put them last, so they get searched shallower and only get a full search if one of them unexpectedly beats alpha.

Check extensions. When you are in check the position is forcing and the evaluation is not worth much, so it searches a ply further before believing it.

Futility and late move pruning. Close to the leaves, if the static evaluation is far enough below alpha that no quiet move is plausibly going to recover it, the quiet moves get skipped.

Quiescence search. This is the one that matters most. Stopping at a fixed depth means you sometimes stop in the middle of an exchange, and an engine that counts up the material after taking a queen but before losing its own will give pieces away all day. So at the leaves it carries on searching captures only, until the position is quiet, with delta pruning to skip the captures that could not recover the deficit anyway.

Underneath all of that is a transposition table keyed on a Zobrist hash. Each position has a hash built out of XORs, which means making a move updates it incrementally rather than rebuilding it, and positions you reach through different move orders land on the same entry so the earlier result gets reused.

Move ordering

How well alpha-beta prunes depends almost entirely on move ordering, so the ordering is a small priority scheme: the transposition table's best move goes first, then captures sorted by most valuable victim and least valuable attacker, then killer moves, which are quiet moves that caused a cutoff at the same depth somewhere else, then counter-moves, and finally a history heuristic scoring moves by how often they have caused cutoffs anywhere at all.

Evaluation

Material and piece-square tables. Every piece has a value and a 25-entry table that nudges it towards the squares that suit it. The Right ends up worth roughly twice a queen, which looks like a mistake and is not, because on a board this small a piece moving as both a rook and a knight covers an enormous proportion of the squares.

Porting it, and being wrong three times

I wanted the engine running on this site, which meant JavaScript. Most of it came across mechanically but the magics did not, because magic indexing needs a 64-bit multiply that wraps, and JavaScript numbers are doubles, its bitwise operators cut everything down to 32 bits, and BigInt is far too slow to be sitting inside a search loop.

What fixes it is Math.imul, which is a 32-bit multiply that wraps, so exactly the semantics magic indexing wants but at half the width. On 25 squares the occupancy that matters is at most six bits, so the tables are tiny and there are plenty of 32-bit magics to find. I searched for a new set and checked each one exhaustively.

Then the browser version started hanging pieces. It would give away a knight, or the Right, and every so often a queen, and the Python one never did any of that.

Having two engines that ought to agree made this much easier, since the Python one works as an oracle. I ran the JavaScript engine headless under Node and compared the two directly, and the attack sets came out bit-identical over 150,000 random lookups, perft matched exactly down to depth four and the evaluation was identical across hundreds of random positions. That ruled out move generation, make and unmake, and the evaluation, which was the useful half of the answer, and left the search.

There were three things wrong with it.

The null-move window. I had written the null-move search with a null window, which is the normal thing to do. At the root though the window is infinite, and negating infinity to build the child's window gave a degenerate bound that the child satisfied straight away. It came back as positive infinity, which cleared beta, and the engine decided that doing nothing was already winning by force. After that it played whatever fell out of a search full of mate scores that did not exist.

The check extension. The Python works out an effective depth to decide whether to drop into quiescence, but it still recurses on the original depth. My port incremented the depth itself, so going down a forcing line every check pushed it back up again and it never came down. An extension that never terminates just runs the search away, and it was inventing mates that were not there either.

Mate scores in the table. The Python stores mate as plus or minus infinity, which survives being written at one depth and read back at another. I had swapped that for a finite score counting the distance to mate, which does not survive it unless you adjust the score by the current ply on the way in and again on the way out, and I had not been doing that. So a mate found deep in the tree came back looking a lot closer than it actually was.

Each of the three was somewhere the Python was relying on a property I had dropped without noticing in translation, and none of them showed up in the diff.

What is left

Even after the fixes the browser engine still disagrees with the Python on about one position in forty and picks a move a few hundred centipawns worse. That is not a bug though. The Python has pruning refinements the port never got, so at equal depth it is simply the stronger searcher, and I would rather write that down than pretend the two are equivalent.

At 350 milliseconds a move the JavaScript version reaches depth ten or eleven, around 400,000 nodes. The source is unminified, so js/chess.js is all there if you want to read it.
